# Playground の作品提出方法の変更計画

作成日：2026年11月4日

本書は計画書です。ここに記載する素材管理、ZIP出力、新しい提出画面、サーバー側の変更は、まだ実装していません。

## 1. 目的と方針

Playground からシナリオや画像・音声をサーバーへ直接アップロードする方式を廃止します。代わりに、作品一式を利用者のブラウザーでZIPにまとめ、利用者自身がギガファイル便にアップロードします。

Playground から管理者へ送るのは、そのダウンロードURLと投稿情報だけにします。管理者が内容を確認してから公開する運用は維持します。

確認済みの方針は、次のとおりです。

- 受け口は、既存の `upload.php` をURL・投稿情報の受け取り専用に変更する。
- 素材管理を先に実装し、登録済みの素材をZIPにまとめる。
- 既存のファイル直接送信機能は、画面だけでなくコードも削除する。
- 添付画像で確認した既存の投稿項目（連絡先・分類・難易度・シナリオ紹介・作者より）は、新しい提出画面でも維持し、URLと一緒に送る。
- 画像・音声のファイル本体はZIPに収録する。投稿情報を維持するために、ファイルの直接送信を再開することはしない。

## 2. この方式の評価

この方式を推奨します。サーバーが利用者のファイルを直接受け取らなくなるため、ファイルの保存・公開に関するリスクと管理負担を減らせます。ZIPは利用者のバックアップにもなり、作品を一式で提出できます。

ただし、URLを受け取るだけで安全になるわけではありません。次の点を運用・実装の両方で扱います。

| 注意点 | 対応方針 |
|---|---|
| 受け口へのスパム・大量送信 | サーバー側の入力検査、送信回数制限、ボット対策を行う |
| ダウンロードURLの期限切れ | 保持期限も送信し、管理者が期限までに取得する。期限切れの場合は再アップロードを依頼する |
| URLを知る第三者による取得 | ダウンロードキーの設定を勧める。ただし、URLとキーを同じ提出経路で送るため、別経路で共有する場合と同じ保護にはならない |
| 外部サービスへの依存 | サービスの仕様変更・障害に備え、既存のGitHub Discussions経由の提出も案内する |
| 外部サイトとの行き来 | 提出画面に手順を示し、別タブから戻って作業を続けられるようにする |
| ZIP内の不正・不要なファイル | 作者に収録内容の確認を促し、管理者も公開前に内容を検査する |
| ブラウザーの保存容量・メモリー不足 | 保存・ZIP作成の失敗を明示し、成功したように表示しない |

ギガファイル便の保持期間の選択肢、ダウンロードキーの仕様、サイズ制限、ファイル名の扱いは、案内文を確定する前に現在の仕様を確認します。具体的な数値は、この計画では固定しません。

## 3. 現状と変更範囲

現在のPlaygroundは、旧 `upload.php` へシナリオと添付ファイルを直接送っています。合計8MBの制限があり、`no-cors` による送信のため、画面から受付結果を確認できません。

素材管理とZIP出力は、[Playground入門](./manual-playground.md)では更新予定として案内されていますが、未実装です。

今回の変更は、次の三つを区別して進めます。

1. **作品の保管**：シナリオと素材をブラウザー内に保存する。
2. **作品一式の取り出し**：シナリオと登録素材をZIPとして保存する。
3. **管理者への提出**：外部にアップロードしたZIPのURLと投稿情報を送る。

ブラウザー内への保存、提出の受付、作品の公開は、それぞれ別の状態です。

## 4. 送信する情報

### 4.1 既存画面から維持する投稿項目

| 項目 | 入力・検査・初期値 |
|---|---|
| 連絡先（メールアドレス） | 必須。メールアドレスの形式を確認する。「公開時の連絡先」としての利用を入力欄に明示する |
| 分類 | カンマ区切り。シナリオのキーワードを初期値にする。サーバー側でも文字数に上限を設ける |
| 難易度 | 1～5。既存の選択肢を維持し、範囲外の値は受け付けない |
| シナリオ紹介 | 必須、2～300文字。シナリオの紹介文を初期値にする |
| 作者より | 必須。「80文字程度」を目安として案内する。厳密な80文字制限とは区別し、サーバー側の上限は別途定める |

これらの投稿情報は、ZIPのURLと同じ受付にひも付けて、管理者への通知と非公開の受付記録に含めます。ZIPのURLだけを通知して、投稿情報が失われる構成にはしません。

シナリオのキーワード・紹介文がある場合はそれを優先するなど、既存の初期値の挙動を引き継ぎます。連絡先などの再入力を減らす仕組みも維持しますが、保存する項目と保存期間は実装前に整理します。ダウンロードキーは安易に永続保存しません。

### 4.2 作品情報

| 項目 | 扱い |
|---|---|
| シナリオID | シナリオから取得し、提出前に確認する。未設定・不正な場合はZIP作成前に修正を促す |
| 作品名 | シナリオから取得し、提出前に確認する |
| 作者名 | シナリオから取得し、提出前に確認する |

提出のために一時的に補った情報と、シナリオ本体の情報が食い違わないようにします。

### 4.3 ZIPの受け渡し情報

| 項目 | 扱い |
|---|---|
| ギガファイル便のダウンロードURL | 必須。HTTPSと許可したホストを検査する |
| 保持期限 | 必須。期限切れの場合は送信前に修正を促す |
| ダウンロードキー | 設定した場合に入力する |

サーバーはURLを受け取っても、自動的にアクセス・ダウンロード・展開しません。管理者が確認して取得します。

## 5. 作者の操作フロー

### 手順1：作品と素材を確認する

- ［検査］と［試遊］で確認する。
- 素材管理に必要な画像・音声を登録する。
- 素材の不足、未使用素材、作者名、ライセンスを確認する。

検査結果は、提出を止めるエラーと、確認を促す警告に分けます。共通素材まで「未登録の素材」と誤判定しないようにします。

### 手順2：提出画面を開く

既存の［投稿…］を、新しい［提出…］に置き換えます。画面には、ZIPの保存、外部へのアップロード、投稿情報の送信という流れを示します。

### 手順3：ZIPを保存する

- 収録内容と合計サイズを表示する。
- シナリオ本体と登録素材を `<id>.zip` としてダウンロードする。
- 作品を変更した場合は、改めてZIPを作成してアップロードする必要があることを案内する。
- ブラウザーから実際の保存完了を確認できない場合は、「保存完了」と断定せず、ダウンロード先の確認を促す。

ZIP作成時の作品情報を保持し、後から編集された作品の情報と、すでにアップロードしたZIPの情報を混在させないようにします。

### 手順4：ギガファイル便にアップロードする

- ［ギガファイル便を開く］で新しいタブを開く。
- 利用者がZIPをアップロードする。
- 管理者が取得できる十分な保持期間を選ぶよう案内する。
- ダウンロードキーの設定を勧める。
- アップロード完了後、ダウンロードURLをコピーしてPlaygroundに戻る。

ギガファイル便への自動アップロードや、同サイトの画面操作の自動化は行いません。

### 手順5：投稿情報とURLを入力する

既存画面の次の5項目を維持します。

- 連絡先（メールアドレス）
- 分類
- 難易度
- シナリオ紹介
- 作者より

同じ画面で、ダウンロードURL・保持期限・ダウンロードキーを入力します。作品名・作者名なども確認できるようにします。

### 手順6：確認して送信する

送信前に、作品情報・投稿情報・URL・期限をまとめて確認します。

Playgroundから送るのはテキスト情報だけです。シナリオJSON、画像、音声、ZIPのファイル本体は送信しません。

### 手順7：受付結果を確認する

- サーバーが受付を完了した場合は、受付番号を表示する。
- 受付と公開は別であることを案内する。
- 入力エラーや通信失敗の場合は内容を表示し、入力を失わずに修正・再試行できるようにする。
- タイムアウトなどで受付の成否が不明な場合は、その旨を明示する。重複送信を防ぐ仕組みも設ける。
- 必要に応じて提出用の定型文をコピーし、既存のGitHub Discussions経由で提出できるようにする。公開の投稿欄へ連絡先やキーを不用意に貼らないよう、コピー対象を分ける。

## 6. ZIPの構成

既存の案内に合わせ、シナリオごとのフォルダー構成にします。

```text
forest01/
  scenario.json
  capture/
    intro.png
    hut.png
  bgm/
    main.mp3
    se/
      door.mp3
```

- 登録済み素材は、未使用のものも含めて収録する。提出前に一覧から確認・削除できるようにする。
- 使用していないフォルダーは作らない。
- シナリオ固有のキャラクター画像を扱う場合は、既存の素材参照仕様に合わせて配置する。
- 共通素材とプレイヤー本体は収録しない。したがって、ZIP単体で動くアプリではない。
- ZIP内のパスやシナリオIDを検査し、フォルダーの外を指す名前や重複した参照先を許さない。
- ローカル保存用ZIPに、連絡先・ダウンロードキーなどの提出情報を不用意に含めない。

## 7. サーバー側の要件

### 7.1 受け付けるデータ

- POSTのテキスト項目だけを受け付ける。
- 添付ファイルがあるリクエストは拒否する。
- 本文サイズと各項目の文字数に上限を設ける。本文は16KB程度を初期案とし、日本語の文字数・バイト数を踏まえて確定する。
- ブラウザー側の検査に頼らず、サーバー側でも必須項目・形式・範囲を確認する。
- URLは文字列の部分一致ではなく、URLとして解析したホスト名を許可リストと照合する。
- 最初はギガファイル便だけを対象とし、他サービスの追加は個別に判断する。

### 7.2 記録と通知

- 投稿情報とURLを非公開の受付記録に保存し、管理者に通知する。
- 公開フォルダーへのファイル保存や、受付と同時の作品公開は行わない。
- 通知メールへの不正なヘッダー挿入を防ぐ。利用者の入力を送信元に使わない。
- メールアドレス・URL・キーを、公開ログやエラー表示に出さない。
- 記録する情報の保存期間・削除方法を定める。
- 通知失敗時も、受付記録の有無と整合した結果を返す。通知できなかった投稿を放置しない運用を用意する。

### 7.3 通信と悪用対策

- CORSは本番のGitHub Pagesのオリジンに限定する。開発用の許可は本番と分ける。
- CORSだけを悪用対策とせず、送信回数制限やボット対策を別途設ける。
- 受付成功・入力エラー・サーバーエラーを区別し、HTTPステータスとJSONで返す。
- `no-cors` による結果不明の送信は廃止する。
- 重複送信を防ぐための受付用トークンなどを設計する。ブラウザーごとの旧投稿者キーを本人確認には使わない。
- 旧ファイル受け取り処理をサーバーでも停止する。Playgroundから呼ばなくするだけで済ませない。

## 8. 管理者の操作フロー

1. 通知と受付記録で、作品情報・投稿情報・URL・保持期限を確認する。
2. 期限までにZIPを取得する。
3. 展開前に、パス・ファイル種別・サイズ・構成を確認する。ZIP内のファイルを不用意に実行しない。
4. シナリオの検査、素材の確認、試遊を行う。
5. 必要に応じて作者に修正を依頼する。
6. 確認後、`scenarios/<id>/` に配置し、公開する。

任意の追加機能として、ZIPの構成・パス・サイズ・シナリオを確認するCLIを検討します。コマンド名や実装範囲は未決定です。

## 9. 実装フェーズ

各フェーズをPR単位で進めます。素材管理は変更範囲が大きいため、着手前に設計と工数を報告します。

| フェーズ | 内容 | 規模・前提 |
|---|---|---|
| P0 | 旧ファイル直接送信機能を削除し、当面の代替提出先を案内する。投稿項目の定義・初期値・検査は再利用可能な部分を残す | 小。サーバー側の旧処理停止も別途必要 |
| P1 | `upload.php` をURL・投稿情報専用に変更する。受付記録、通知、結果応答、悪用対策を用意する | 中。PHPの管理場所・運用方法の決定が必要 |
| P2 | IndexedDBによる素材管理、追加・一覧・差し替え・削除、試遊への接続、保存失敗の表示を実装する | 大。事前の設計確認が必要 |
| P3 | シナリオと登録素材のZIP出力を実装する | 中。P2が前提 |
| P4 | 新しい提出画面を実装する。既存5項目を維持し、作品情報・URL・期限・キーと一緒に送る | 中。P0・P1・P3が前提 |
| P5 | 任意で管理者向けZIP検査CLIを追加する | 小～中。P3の収録仕様確定が前提 |

ZIPから編集内容を復元する読み込み機能も有用ですが、今回の提出機能に必須とはせず、範囲を別途確認します。

## 10. 確認項目

- ZIPにシナリオと登録素材が入り、フォルダー構成と参照が一致すること。
- 共通素材や提出者の連絡先・キーが、ZIPに混入しないこと。
- 素材の不足・未使用、保存失敗、ZIP生成失敗を適切に表示すること。
- 既存5項目と作品情報・URL・期限・キーが、管理者の受付記録・通知に届くこと。
- 日本語の紹介文、文字数の境界値、難易度の範囲外、期限切れ、許可していないURLを検査すること。
- サーバーへファイルを直接送れないこと。
- 受付成功・入力エラー・通信失敗・成否不明を区別し、失敗時に入力が失われないこと。
- 同じ内容の再試行が、無用な重複受付や重複通知につながらないこと。
- 管理者の通知失敗を検知し、受付を見落とさないこと。
- 別タブとの行き来、スマートフォン、キーボード操作でも手順を進められること。
- 既存のJSON保存・読み込み・試遊などの動作を維持すること。

## 12. 実装前に確定する事項

1. PHPのコードを管理する場所と、本番への反映・旧処理停止の手順。
2. 送信者への確認メールを残すか。画面で受付結果を確認できるため、まずは管理者通知だけにする案を推奨する。
3. ギガファイル便で推奨する保持期間と、現在のサービス仕様。
4. 各テキスト項目の最大長、受付記録の保存期間、送信回数制限、ボット対策。
5. IndexedDBのデータ構造、素材参照の対応付け、保存・移行・復旧方法。
6. ZIP生成方法と、ブラウザーで無理なく扱えるサイズの目安。音声・画像は圧縮済みのものが多いため、圧縮率だけでなくメモリー使用量と信頼性を優先する。
7. ZIP読み込みによる復元と、管理者向け検査CLIを今回の範囲に含めるか。
