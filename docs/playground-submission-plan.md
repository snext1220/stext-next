# Playground の作品提出方法の変更計画

作成日：2026年11月4日

更新日：2026年11月4日（オレンジフォームのHTML組み込みを第一候補に変更）

データ管理との整合方針：[ローカルリソース管理・ZIP出力機能仕様書](./Playground-data-management.md)と、共通素材の除外、生成前の保存完了とスナップショット取得、未登録の固有素材の不足通知、シナリオIDの扱いを統一する。

本書は計画書です。ここに記載する素材管理、ZIP出力、新しい提出案内、外部フォームの設定、旧サーバーの受け口の停止は、まだ実施していません。

## 1. 目的と方針

Playground からシナリオや画像・音声をサーバーへ直接アップロードする方式を廃止します。代わりに、作品一式を利用者のブラウザーでZIPにまとめ、利用者自身がギガファイル便にアップロードします。

Playground内に[オレンジフォーム](https://orange-cloud7.net/form/)のHTMLフォームを組み込み、利用者がダウンロードURLと投稿情報を送信します。表示・初期値の設定はPlaygroundが担当し、受付・保管・通知はオレンジフォームに任せます。Playground独自の受け口は作りません。管理者が内容を確認してから公開する運用は維持します。

確認済みの方針は、次のとおりです。

- 受け口にはオレンジフォームを使う。以前の「`upload.php` をURL専用に改修する」案は取りやめ、旧受け口を停止する。
- 素材管理を先に実装し、登録済みの素材をZIPにまとめる。
- 既存のファイル直接送信機能は、画面だけでなくコードも削除する。
- 添付画像で確認した既存の投稿項目（連絡先・分類・難易度・シナリオ紹介・作者より）は、オレンジフォームでも維持し、URLと一緒に送る。
- 画像・音声のファイル本体はZIPに収録する。投稿情報を維持するために、ファイルの直接送信を再開することはしない。
- 専用フォームの発行HTMLに従い、Playground内にフォームを組み込む方式を第一候補にする。通常のHTMLフォーム送信を使い、独自のAPI連携は前提にしない。外部フォームへのリンクは代替手段にする。

## 2. この方式の評価

この方式を推奨します。自前のサーバーでファイルや投稿情報を受け取る処理を持たずに済み、受け口の保守負担を減らせます。ZIPは利用者のバックアップにもなり、作品を一式で提出できます。ただし、投稿情報の保管・通知を外部サービスへ委ねるため、アカウント管理や個人情報の扱いは引き続き必要です。

ただし、URLを受け取るだけで安全になるわけではありません。次の点を運用・実装の両方で扱います。

| 注意点 | 対応方針 |
|---|---|
| 受け口へのスパム・大量送信 | 採用するフォームとプランの迷惑投稿対策を確認する。CAPTCHAや送信回数制限が利用できるとは未確認の段階で断定しない |
| ダウンロードURLの期限切れ | 保持期限も送信し、管理者が期限までに取得する。期限切れの場合は再アップロードを依頼する |
| URLを知る第三者による取得 | ダウンロードキーの設定を勧める。ただし、URLとキーを同じ提出経路で送るため、別経路で共有する場合と同じ保護にはならない |
| 外部サービスへの依存 | 両サービスの仕様変更・障害に備え、既存のGitHub Discussions経由の提出も案内する |
| 入力項目の制限 | 必須設定・文字数・URL形式・保持期限の検査能力を確認する。独自サーバーと同等の検査を保証せず、不足部分は管理者が確認する |
| 投稿情報・連絡先の外部保管 | 利用目的と外部サービスの利用を明示し、保管期間・削除・閲覧権限を決める。連絡先を自動的に公開しない |
| 完了状態の連携 | フォームを送出しただけでは受付完了にしない。Playgroundから別オリジンの確認・完了ページの内容は通常確認できない |
| 広告・料金・機能変更 | 無料版の広告と利用条件を確認する。広告非表示が必要なら有料版を検討する |
| URL・キーの漏えい | 連絡先、ダウンロードURL、キーを事前入力用URLのクエリに載せない。通知・CSVなどの複製先も管理する |
| 外部サイトとの行き来 | 入力はPlayground内で行い、送信先の確認・完了ページは別タブに表示する案を基本にする。ギガファイル便との行き来も案内する |
| ZIP内の不正・不要なファイル | 作者に収録内容の確認を促し、管理者も公開前に内容を検査する |
| ブラウザーの保存容量・メモリー不足 | 保存・ZIP作成の失敗を明示し、成功したように表示しない |

ギガファイル便の保持期間の選択肢、ダウンロードキーの仕様、サイズ制限、ファイル名の扱いは、案内文を確定する前に現在の仕様を確認します。具体的な数値は、この計画では固定しません。

### 2.1 オレンジフォームの公式情報と未確認事項

2026年11月4日に[公式案内](https://orange-cloud7.net/form/)と[料金・機能案内](https://orange-cloud7.net/form/price/)で、次の説明を確認しました。

- オリジナルの入力項目を設定できる。
- 登録データをCSVでダウンロードできる。
- 登録完了ページの編集・転送と、自動返信メールの設定ができる。
- 基本情報をCookieに記憶する機能がある。
- HTML/CSSのカスタマイズや埋め込みHTMLに関する説明がある。
- 広告非表示はビジネス版の機能として案内されている。
- 新しいフォームと従来のフォームがあり、採用する種類ごとの確認が必要。

上記は提供元の案内であり、実際に作成したフォームの動作検証や安全性の保証ではありません。管理者通知の項目・配送失敗時の確認方法、入力検査、迷惑投稿対策、保存期間、利用上限、受付番号、重複対策、事前入力の公式サポートは、採用するフォームとプランで別途確認します。HTML埋め込みの案内を、APIや任意の直接POSTがサポートされる根拠にはしません。

### 2.2 HTML組み込みの利用例

利用者から提示された[WINGSプロジェクトのお問い合わせ画面](https://wings.web-deli.com/contact?type=member)のHTMLを2026年11月4日に確認しました。問い合わせの送信は行っていません。

- サイトのページ内に、iframeではなく通常のHTMLフォームを置いている。
- `action="https://form.os7.biz/form/submit"`、`method="post"` でオレンジフォームへ送っている。
- `form_id`、`encoding_test`、`base_url`、`urlhash`、`oid` などのhidden項目を持ち、入力欄に `mail` や `free...` などの送信用の名前を付けている。
- `target="other"` を指定しており、送信先は名前付きの別閲覧コンテキストになる。実際のタブ・ウィンドウの表示はブラウザーに依存する。

この構成を参考に、Playgroundの専用フォームから発行した項目名・hidden値を使ってReact内に組み込みます。利用例のフォームIDや送信先アカウントの設定値は流用しません。通常のHTMLフォームによる別オリジンへの画面遷移には、`fetch` と同じCORS許可は不要ですが、送信先が受け付けるか、確認ページへ進むか、最終受付・通知が成功するかは専用フォームで検証します。

## 3. 現状と変更範囲

現在のPlaygroundは、旧 `upload.php` へシナリオと添付ファイルを直接送っています。合計8MBの制限があり、`no-cors` による送信のため、画面から受付結果を確認できません。

素材管理とZIP出力は、[Playground入門](./manual-playground.md)では更新予定として案内されていますが、未実装です。

今回の変更は、次の三つを区別して進めます。

1. **作品の保管**：シナリオと素材をブラウザー内に保存する。
2. **作品一式の取り出し**：シナリオと登録素材をZIPとして保存する。
3. **管理者への提出**：オレンジフォームで、外部にアップロードしたZIPのURLと投稿情報を送る。

ブラウザー内への保存、提出の受付、作品の公開は、それぞれ別の状態です。

## 4. 送信する情報

### 4.1 既存画面から維持する投稿項目

| 項目 | 入力・検査・初期値 |
|---|---|
| 連絡先（メールアドレス） | 必須。メールアドレス用の項目を使う。提出に関する連絡に利用し、公開する場合は別途明示して同意を得る |
| 分類 | カンマ区切り。シナリオのキーワードを転記できるようにする。フォーム側の文字数制限を確認する |
| 難易度 | 1～5。既存の選択肢を維持し、範囲外の値は受け付けない |
| シナリオ紹介 | 必須、2～300文字。シナリオの紹介文を転記できるようにする。最小・最大文字数をフォーム側で制限できるか確認する |
| 作者より | 必須。「80文字程度」を目安として案内する。厳密な80文字制限とは区別し、フォーム側で設定可能な上限を確認する |

これらの投稿情報は、ZIPのURLと同じ受付にひも付けて、管理者への通知と非公開の受付記録に含めます。ZIPのURLだけを通知して、投稿情報が失われる構成にはしません。

Playground内の入力欄には、ZIP作成時の作品情報・キーワード・紹介文を初期値として設定します。専用フォームから発行された項目名に対応付け、通常のHTMLフォーム送信に含めます。外部フォームの事前入力用URLやAPIに依存する必要はありません。外部フォームへ移動する代替手段のため、作品情報をコピーできる表示も用意します。

連絡先・ダウンロードキーなどは、組み込み画面での入力中だけ保持し、新たな永続保存を追加しません。外部サービスのCookie保存機能が組み込みでも動くとは仮定せず、使う場合は保存対象を確認します。

### 4.2 作品情報

| 項目 | 扱い |
|---|---|
| シナリオID | シナリオから取得する。未設定・不正な場合はZIP作成前に本体の修正を促し、修正完了まではZIPを生成しない |
| 作品名 | シナリオから取得し、提出前に確認する |
| 作者名 | シナリオから取得し、提出前に確認する |

提出のために一時的に補った情報と、シナリオ本体の情報が食い違わないようにします。

IDが未設定・不正でもローカル編集・素材登録は可能とします。ローカル作品の識別は公開用IDだけに依存させず、IDの設定・変更で素材を見失ったり、同じIDの別作品と素材が混ざったりしないようにします。内部の識別方法と、同じIDのJSONを読み込む際の操作は、データ管理の実装前に設計します。

### 4.3 ZIPの受け渡し情報

| 項目 | 扱い |
|---|---|
| ギガファイル便のダウンロードURL | 必須。HTTPSのギガファイル便URLを案内し、フォームで制限できる範囲を確認する。管理者もホスト名を確認する |
| 保持期限 | 必須。入力形式と、期限切れを検出できるかを確認する。管理者も取得前に確認する |
| ダウンロードキー | 設定した場合に入力する |

プロジェクト側でURLへの自動アクセス・ダウンロード・展開は実装しません。管理者が確認して取得します。外部フォーム・通知先によるリンク処理の仕様は別途確認します。

## 5. 作者の操作フロー

### 手順1：作品と素材を確認する

- ［検査］と［試遊］で確認する。
- 素材管理に必要な画像・音声を登録する。
- 素材の不足、未使用素材、作者名、ライセンスを確認する。

検査結果は、提出を止めるエラーと、確認を促す警告に分けます。共通素材まで「未登録の素材」と誤判定しないようにします。

シナリオ固有素材は、従来の外部配信先で表示・再生できても、ローカルに未登録なら不足として対象パスを通知します。試遊できることを、提出ZIPに素材がそろっている根拠にはしません。外部配信先から自動取得して不足を隠すことも行いません。

### 手順2：提出画面を開く

既存の［投稿…］を、新しい［提出…］に置き換えます。Playground内には、ZIPの保存、ギガファイル便へのアップロード、投稿情報の送信という案内と、オレンジフォームに送る入力画面を表示します。

### 手順3：ZIPを保存する

- 収録内容と合計サイズを表示する。
- シナリオIDを確認し、保留中のシナリオ編集・素材操作の保存を完了する。保存に失敗した場合は通知してZIP生成を中止し、古い保存内容で代替しない。
- 保存完了後、シナリオJSONと登録素材の同一時点のスナップショットを取得する。取得中の変更が混ざらないようにし、その後の編集は生成するZIPに反映しない。
- シナリオ本体と登録素材を `<id>.zip` としてダウンロードする。
- 作品を変更した場合は、改めてZIPを作成してアップロードする必要があることを案内する。
- ブラウザーから実際の保存完了を確認できない場合は、「保存完了」と断定せず、ダウンロード先の確認を促す。

ZIP作成に使ったスナップショットの作品情報・分類・紹介文を投稿フォームの初期値に使い、後から編集された作品の情報と、すでにアップロードしたZIPの情報を混在させないようにします。スナップショット取得後のZIP生成処理自体は、保存データを削除・変更しません。

### 手順4：ギガファイル便にアップロードする

- ［ギガファイル便を開く］で新しいタブを開く。
- 利用者がZIPをアップロードする。
- 管理者が取得できる十分な保持期間を選ぶよう案内する。
- ダウンロードキーの設定を勧める。
- アップロード完了後、ダウンロードURL・保持期限・キーを控えてPlaygroundに戻る。

ギガファイル便への自動アップロードや、同サイトの画面操作の自動化は行いません。

### 手順5：投稿情報とURLを入力する

既存画面の次の5項目を維持します。

- 連絡先（メールアドレス）
- 分類
- 難易度
- シナリオ紹介
- 作者より

Playground内の組み込みフォームで、上記5項目と、作品情報・ダウンロードURL・保持期限・ダウンロードキーを確認・入力します。作品名・作者名・分類・紹介文などはシナリオから初期値を設定します。

組み込みには通常のHTMLフォームを使い、iframeは前提にしません。入力値やhidden項目はReactの要素として構成し、フォーム全体のHTML文字列をそのまま挿入する方式は避けます。オレンジフォームが提供する必須のスクリプト等があれば、Reactとの互換性を確認します。利用者の明示的な送信操作なしに送信することはありません。

### 手順6：確認して送信する

Playground内で入力を確認し、［確認・送信へ］などのボタンで、発行HTMLに従った通常のPOSTを行います。送信先の確認・完了ページは別タブに表示し、編集中のPlaygroundを残す案を基本にします。ボタン名・案内は、実際に確認画面を挟むかどうかに合わせます。

フォームから送るのはテキスト情報だけです。シナリオJSON、画像、音声、ZIPのファイル本体は送信しません。ファイル添付欄は設けません。

### 手順7：受付結果を確認する

- オレンジフォームの送信完了画面で受付を確認する。受付番号が使えるかは確認し、利用できると仮定しない。
- 完了画面には、受付と公開は別であることと、必要ならPlaygroundに戻るリンクを案内する。
- Playgroundでは、POSTの開始や、戻るリンクから帰ってきたことを「送信成功」の根拠にしない。
- Playgroundの入力は画面が開いている間保持する。送信先での入力エラー・通信失敗・再試行・重複対策も確認し、成功応答を読み取れない状態で入力を自動消去しない。
- 成否が不明な場合の問い合わせ方法を示す。連打・再投稿による重複の可能性は管理者側でも確認する。
- 必要に応じて提出用の定型文をコピーし、既存のGitHub Discussions経由で提出できるようにする。公開の投稿欄へ連絡先やキーを不用意に貼らないよう、コピー対象を分ける。

代替の提出先：<https://github.com/snext1220/stext/discussions/299>

## 6. ZIPの構成

既存の案内に合わせ、シナリオごとのフォルダー構成にします。

```text
forest01/
  scenario.json
  capture/
    intro.png
    hut.png
  bgm/
    main.mp3
    se/
      door.mp3
```

- 出力対象のシナリオの登録済み固有素材は、未使用のものも含めて収録する。別作品の素材は収録しない。提出前に一覧から確認・削除できるようにする。
- 使用していないフォルダーは作らない。
- シナリオ固有のキャラクター画像を扱う場合は、既存の素材参照仕様に合わせて配置する。
- 共通素材とプレイヤー本体は収録せず、共通素材の参照は維持する。したがって、ZIP単体で動くアプリではない。
- ZIP内のパスやシナリオIDを検査し、フォルダーの外を指す名前や重複した参照先を許さない。
- ローカル保存用ZIPに、連絡先・ダウンロードキーなどの提出情報を不用意に含めない。

## 7. 外部フォームの設定と運用要件

### 7.1 フォームの設定

- 第4節の項目を作成し、可能な限り必須設定・選択肢・文字数制限を設定する。
- ファイル添付機能は使わない。独自のアップロード先や中継サーバーも設けない。
- 最初はギガファイル便だけを提出先として案内し、他サービスの追加は個別に判断する。
- URLのホスト制限や期限の検査ができない場合は、入力例と注意書きを置き、管理者が確認する。ブラウザー側の検査だけで受付内容が保証されるとは扱わない。
- 完了画面に、管理者確認後の公開であることを記載する。
- 組み込み用の送信先、項目名、hidden値は専用フォームの発行HTMLを基に設定する。代替リンクには実際の公開フォームURLを使い、サービス紹介ページを提出先にしない。

### 7.2 記録・通知・個人情報

- 投稿情報とURLがフォームの非公開記録に残り、管理者への通知に必要な項目が含まれることを確認する。
- メールだけを受付台帳にせず、管理画面でも定期的に確認する。通知の遅延・迷惑メール振り分けと、ギガファイル便の期限切れに備える。
- 利用目的、外部フォームの利用、連絡先の公開有無、問い合わせ窓口を記載する。利用規約・プライバシーポリシーと適用プランを確認する。
- 閲覧権限を必要な管理者に限定し、利用可能なら多要素認証を設定する。
- 保存期間、CSV出力によるバックアップ、受付終了後の削除手順を決める。通知メールやCSVに複製した情報も対象にする。
- メール配信サービスへの自動登録や、不要なSlack・スプレッドシート等への連携は有効にしない。
- 自動返信は任意とする。使う場合は、悪用対策とキー・URLなどの返信内容を確認する。送信先のメールアドレスが本人のものとは限らない。
- 受付と同時の自動公開は行わない。

### 7.3 連携の境界と旧受け口の停止

- Playgroundからの `fetch` による送信、`no-cors`、独自のJSON応答・CORS設定は不要になる。専用フォームの発行HTMLに従う通常のPOSTを使い、未確認のAPIや独自形式のリクエストへ置き換えない。
- URLパラメーターで機密情報を渡さない。事前入力機能を追加する場合も、公式仕様を確認し、対象を非機密の作品情報に限定する。
- 完了ページから戻る際のURLパラメーターを、受付完了の証明として扱わない。
- 迷惑投稿対策・利用上限・重複制御は、サービスが提供する範囲を確認する。不足する場合はフォームやプランを再検討する。
- 旧 `upload.php` はURL専用へ改修せず、サーバーでも停止する。Playgroundから呼ばなくするだけで済ませない。
- ブラウザーごとの旧投稿者キーを本人確認には使わない。新しい提出経路に旧FTP希望や旧プレビュー生成の処理を引き継がない。

## 8. 管理者の操作フロー

1. オレンジフォームの通知と管理画面で、作品情報・投稿情報・URL・保持期限を確認する。ダウンロード前にURLのホスト名を確認する。
2. 期限までにZIPを取得する。
3. 展開前に、パス・ファイル種別・サイズ・構成を確認する。ZIP内のファイルを不用意に実行しない。
4. シナリオの検査、素材の確認、試遊を行う。
5. 必要に応じて作者に修正を依頼する。
6. 確認後、`scenarios/<id>/` に配置し、公開する。

任意の追加機能として、ZIPの構成・パス・サイズ・シナリオを確認するCLIを検討します。コマンド名や実装範囲は未決定です。

## 9. 実装フェーズ

各フェーズをPR単位で進めます。素材管理は変更範囲が大きいため、着手前に設計と工数を報告します。

| フェーズ | 内容 | 規模・前提 |
|---|---|---|
| P0 | 旧ファイル直接送信機能を削除し、当面の代替提出先を案内する。作品情報のコピーに必要な処理のみ再利用する | 小。サーバー側の旧処理停止も別途必要 |
| P1 | オレンジフォームを作成し、項目・完了画面・通知・迷惑投稿対策・個人情報の運用を設定・検証する | 小～中。フォーム種類とプランの決定が必要。管理画面での設定はPR外の作業として記録する |
| P2 | IndexedDBによる素材管理、追加・一覧・差し替え・削除、試遊への接続、保存失敗の表示を実装する | 大。事前の設計確認が必要 |
| P3 | シナリオと登録素材のZIP出力を実装する | 中。P2が前提 |
| P4 | Playgroundに提出案内とHTMLフォームを組み込み、初期値・入力検査・項目対応・別タブへの通常POSTを実装する。外部フォームへのリンクとコピー機能も代替手段として用意する | 中。P0・P1・P3が前提 |
| P5 | 任意で管理者向けZIP検査CLIを追加する | 小～中。P3の収録仕様確定が前提 |

ZIPから編集内容を復元する読み込み機能も有用ですが、今回の提出機能に必須とはせず、範囲を別途確認します。

## 10. 確認項目

- ZIPにシナリオと登録素材が入り、フォルダー構成と参照が一致すること。
- 共通素材や提出者の連絡先・キーが、ZIPに混入しないこと。
- 素材の不足・未使用、保存失敗、ZIP生成失敗を適切に表示すること。
- 固有素材は外部配信先で表示・再生できても未登録なら不足を通知し、共通素材の未登録は不足扱いにしないこと。
- 編集直後のZIPにも最新の内容が入り、保存失敗時は生成を中止すること。生成中の変更が混ざらず、投稿フォームの初期値も同じスナップショットに基づくこと。
- ID未設定でもローカル編集・素材登録ができ、IDの設定・変更で素材との対応が失われず、同じIDの別作品と素材が混ざらないこと。ZIP生成前にはIDの修正を求めること。
- 既存5項目と作品情報・URL・期限・キーをフォームで入力でき、管理画面の記録・通知に届くこと。
- 日本語の紹介文、文字数の境界値、難易度の範囲外、期限切れ、許可していないURLについて、フォームが制限する範囲と管理者が確認する範囲を検証・記録すること。
- フォームにファイル添付欄がなく、自前の旧受け口も停止していること。
- 外部フォームの入力保持・完了表示・再試行・重複時の挙動を確認し、Playgroundでは未確認の送信成功を表示しないこと。
- 通知が届かない場合も、管理画面から受付を確認できること。
- 連絡先やキーが、事前入力用URL、公開の定型文、意図しない自動返信・連携先に漏れないこと。
- 専用フォームの項目名・hidden値が正しく、Reactによる初期値設定、日本語の送信、確認画面への遷移が動くこと。
- 送信先を別タブに開いても編集中の内容が失われず、送出だけで入力を消去・受付完了表示しないこと。
- 別タブとの行き来、スマートフォン、キーボード操作でも手順を進められること。
- 既存のJSON保存・読み込み・試遊などの動作を維持すること。

## 12. 実装前に確定する事項

1. オレンジフォームの種類・プラン・実際の公開URLと、旧 `upload.php` を停止する担当・手順。
2. 送信者への確認メールを使うか。外部フォームの完了画面で受付を確認する方式を基本に、まずは管理者通知だけにする案を推奨する。
3. ギガファイル便で推奨する保持期間と、現在のサービス仕様。
4. 各項目の検査・文字数制限・迷惑投稿対策・通知・再試行時の挙動が、採用するフォームで要件を満たすか。
5. IndexedDBのデータ構造、素材参照の対応付け、保存・移行・復旧方法。
6. ZIP生成方法と、ブラウザーで無理なく扱えるサイズの目安。音声・画像は圧縮済みのものが多いため、圧縮率だけでなくメモリー使用量と信頼性を優先する。
7. ZIP読み込みによる復元と、管理者向け検査CLIを今回の範囲に含めるか。
8. 投稿情報の保存期間、管理者の権限・認証、バックアップ・削除方法、連絡先を公開する場合の明示と同意。
9. 専用フォームの発行HTML、必須スクリプトの有無、項目対応、確認・完了ページへの遷移、別タブ送信とReact組み込みの動作。
