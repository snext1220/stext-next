# Playground の作品提出方法の変更計画

作成日：2026年11月4日

更新日：2026年11月6日（オレンジフォーム復旧に伴う再採用を反映）

データ管理との整合方針：[ローカルリソース管理・ZIP出力機能仕様書](./Playground-data-management.md)と、共通素材の除外、生成前の保存完了とスナップショット取得、未登録の固有素材の不足通知、シナリオIDの扱いを統一する。

素材管理とZIP出力は実装済みです。オレンジフォームの復旧と正確な発行HTMLの提示を受け、独自PHP受け口を削除し、通常のフォームPOSTに切り替えました。実フォームの確認画面・受付・管理者通知・投稿者への確認メールは、管理画面での設定と実地確認が必要です。

## 1. 目的と方針

Playground からシナリオや画像・音声をサーバーへ直接アップロードする方式は廃止します。作品一式を利用者のブラウザーでZIPにまとめ、利用者自身がギガファイル便にアップロードします。Playgroundは投稿情報とダウンロードURLをHTTPSでオレンジフォームへ送り、別タブで確認・最終送信します。管理者通知と投稿者への確認メールはオレンジフォームの設定で送信します。ZIP本体はオレンジフォームへアップロードしません。管理者が内容を確認してから公開する運用は維持します。

確認済みの方針は、次のとおりです。

- 送信先は `https://form.os7.biz/form/submit/`、フォームIDは `261098`。
- 発行HTMLどおりの項目名・hidden値・honeypotを使う。著作権表示は削除しない。
- 通常のフォームPOSTを使い、外部script、`fetch`、CORSによる応答読み取りは使わない。
- 管理者通知・自動返信・必須設定・迷惑投稿対策・保存期間はオレンジフォームの管理画面で設定する。ソースやブラウザーへ秘密情報を置かない。
- 素材管理を先に実装し、登録済みの素材をZIPにまとめる。
- 既存のファイル直接送信機能は、画面だけでなくコードも削除する。
- 既存の投稿項目（作者名・連絡先・分類・難易度・シナリオ紹介・作者より）を維持し、URL・保持期間・キーと一緒に送る。
- 画像・音声のファイル本体はZIPに収録する。投稿情報を維持するために、ファイルの直接送信を再開することはしない。
- PlaygroundからUTF-8の `application/x-www-form-urlencoded` で送信する。別タブの受付・メール配送結果はPlaygroundから確認できないため、成功とは表示しない。

## 2. この方式の評価

オレンジフォームに受付とメール通知を任せ、独自PHP受け口の保守をなくします。一方、外部サービスの仕様・稼働状況に依存するため、管理画面の設定と個人情報の保管管理が必要です。ZIP本体は受け取らず、利用者のアップロード手順を維持します。

ただし、URLを受け取るだけで安全になるわけではありません。次の点を運用・実装の両方で扱います。

| 注意点 | 対応方針 |
|---|---|
| 受け口へのスパム・大量送信 | 発行HTMLのhoneypotを維持し、オレンジフォーム側の入力検査・迷惑投稿対策を確認する。クライアントの検査だけに頼らない |
| ダウンロードURLの期限切れ | 保持期限も送信し、管理者が期限までに取得する。期限切れの場合は再アップロードを依頼する |
| URLを知る第三者による取得 | ダウンロードキーの設定を勧める。ただし、URLとキーを同じ提出経路で送るため、別経路で共有する場合と同じ保護にはならない |
| 外部サービスへの依存 | 両サービスの仕様変更・障害に備え、既存のGitHub Discussions経由の提出も案内する |
| 入力項目の制限 | Playgroundで必須設定・文字数・URL形式・保持期間を検証し、フォーム側の検査も設定する。ギガファイル便URLであることなど、追加の確認は管理者も行う |
| 投稿情報・連絡先の保管 | オレンジフォームの受付データと受信メールの閲覧権限、保管期間、削除方法を定める |
| 完了状態の連携 | 別タブで確認・最終送信し、受付結果を確認する。Playgroundでは受付成功と断定しない。再試行前に重複投稿を確認する |
| メール配送 | 管理者通知と `mail` 宛ての自動返信を設定し、テスト投稿で到達を実地確認する |
| URL・キーの漏えい | HTTPS POST本文とメールでのみ送信し、URLクエリ、公開の定型文、ログへ含めない。受信メールを管理する |
| クロスオリジン送信 | 通常のフォームPOSTで別タブへ送る。`noopener noreferrer` を指定し、別タブから編集画面へアクセスさせない |
| ZIP内の不正・不要なファイル | 作者に収録内容の確認を促し、管理者も公開前に内容を検査する |
| ブラウザーの保存容量・メモリー不足 | 保存・ZIP作成の失敗を明示し、成功したように表示しない |

ギガファイル便の保持期間の選択肢、ダウンロードキーの仕様、サイズ制限、ファイル名の扱いは、案内文を確定する前に現在の仕様を確認します。具体的な数値は、この計画では固定しません。

### 2.1 オレンジフォームの検討記録

11月5日はオレンジフォームの利用を断念してPHPへ切り替えましたが、11月6日の復旧と発行HTMLの提示を受け、再採用しました。

2026年11月4日に[公式案内](https://orange-cloud7.net/form/)と[料金・機能案内](https://orange-cloud7.net/form/price/)で、次の説明を確認しました。

- オリジナルの入力項目を設定できる。
- 登録データをCSVでダウンロードできる。
- 登録完了ページの編集・転送と、自動返信メールの設定ができる。
- 基本情報をCookieに記憶する機能がある。
- HTML/CSSのカスタマイズや埋め込みHTMLに関する説明がある。
- 広告非表示はビジネス版の機能として案内されている。
- 新しいフォームと従来のフォームがあり、採用する種類ごとの確認が必要。

上記は提供元の案内であり、実際に作成したフォームの動作検証や安全性の保証ではありません。管理者通知の項目・配送失敗時の確認方法、入力検査、迷惑投稿対策、保存期間、利用上限、受付番号、重複対策、事前入力の公式サポートは、採用するフォームとプランで別途確認します。HTML埋め込みの案内を、APIや任意の直接POSTがサポートされる根拠にはしません。

### 2.2 HTML組み込みの利用例

利用者から提示された[WINGSプロジェクトのお問い合わせ画面](https://wings.web-deli.com/contact?type=member)のHTMLを2026年11月4日に確認しました。問い合わせの送信は行っていません。

- サイトのページ内に、iframeではなく通常のHTMLフォームを置いている。
- `action="https://form.os7.biz/form/submit"`、`method="post"` でオレンジフォームへ送っている。
- `form_id`、`encoding_test`、`base_url`、`urlhash`、`oid` などのhidden項目を持ち、入力欄に `mail` や `free...` などの送信用の名前を付けている。
- `target="other"` を指定しており、送信先は名前付きの別閲覧コンテキストになる。実際のタブ・ウィンドウの表示はブラウザーに依存する。

この例は検討時の調査記録です。現在は利用者から提示されたシナリオ投稿フォームの発行HTMLを基に、同様の通常のフォームPOSTを使います。

#### 発行HTMLとの対応

`form_id=261098`、`encoding_test=あいうえお眉幅ABC`、`base_url=https://form.os7.biz/`、`urlhash=f/06d639bb/`、`oid=1012766` をhidden項目として送ります。honeypotは `of_dummy_note` です。2026年11月6日に提供元の `of_lib.js` を読み取り、`OF_submit()` がフォームのaction設定と通常のsubmitを行うことを確認しました。Playgroundではこれをブラウザー標準のフォーム送信に置き換え、jQueryなどの外部scriptは読み込みません。実フォームへの送信は行っていません。

## 3. 現状と変更範囲

旧 `upload.php` への直接送信と8MB制限は、Playgroundのクライアントコードから削除しました。サーバー側の旧受け口はまだ停止していません。

素材管理とZIP出力は実装済みです。提出画面では保存済みスナップショットと素材を使ってZIPを作成し、作品名・IDを読み取り専用で表示します。

今回の変更は、次の三つを区別して進めます。

1. **作品の保管**：シナリオと素材をブラウザー内に保存する。
2. **作品一式の取り出し**：シナリオと登録素材をZIPとして保存する。
3. **管理者への提出**：オレンジフォームで、外部にアップロードしたZIPのURLと投稿情報を受け付け、管理者通知と投稿者への確認メールを送る。

ブラウザー内への保存、提出の受付、作品の公開は、それぞれ別の状態です。

## 4. 送信する情報

### 4.1 既存画面から維持する投稿項目

| 項目 | 入力・検査・初期値 |
|---|---|
| 連絡先（メールアドレス） | 必須。メールアドレス用の項目を使う。提出に関する連絡に利用し、公開する場合は別途明示して同意を得る |
| 分類 | 必須、カンマ区切り。シナリオのキーワードを転記できるようにする。フォーム側の文字数制限を確認する |
| 難易度 | 1～5。既存の選択肢を維持し、範囲外の値は受け付けない |
| シナリオ紹介 | 必須、2～300文字。シナリオの紹介文を転記できるようにする。最小・最大文字数をフォーム側で制限できるか確認する |
| 作者より | 必須。「80文字程度」を目安として案内する。厳密な80文字制限とは区別し、フォーム側で設定可能な上限を確認する |

これらの投稿情報は、ZIPのURLとともにオレンジフォームへ送ります。フォーム側の受付データと通知メールの保管を管理します。

Playground内の入力欄には、シナリオ情報・キーワード・紹介文を初期値として設定します。送信項目名は、作者名 `single_seimei`、メール `mail`、分類 `free1`、難易度 `free2`、紹介 `free3`、作者より `free4`、URL `free5`、保持期間 `free6`、キー `free7` です。GitHub Discussionsはダイアログ下部の補足リンクのみとし、提出文のコピー機能は廃止します。

ダウンロードキー以外の入力内容（メールアドレスを含む）は、プロジェクトごとのCookieに30日間保存し、ダイアログを閉じても復元します。入力変更時に保存期間を更新し、保存失敗は警告します。［保存した入力内容を削除］で、この作品のCookieを削除して入力欄を初期値に戻せます。ダウンロードキーは保存せず、開くたびに入力します。オレンジフォームへの送信後は、受付データとメールボックスの閲覧権限・保管期間を管理します。確認メールにURL・キーを含めるかは、必要性を確認して管理画面で設定します。

### 4.2 作品情報

| 項目 | 扱い |
|---|---|
| シナリオID | ZIP内の `scenario.json` から確認する。未設定・不正な場合はZIP作成と提出を止め、本体の修正を促す。画面では読み取り専用で表示し、受付フォームには送らない |
| 作品名 | ZIP内の `scenario.json` から確認する。画面では読み取り専用で表示し、受付フォームには送らない |
| 作者名 | シナリオから初期値を設定する。提出画面で編集し、`single_seimei` として送る |

提出のために一時的に補った情報と、シナリオ本体の情報が食い違わないようにします。

IDが未設定・不正でもローカル編集・素材登録は可能とします。ローカル作品の識別は公開用IDだけに依存させず、IDの設定・変更で素材を見失ったり、同じIDの別作品と素材が混ざったりしないようにします。内部の識別方法と、同じIDのJSONを読み込む際の操作は、データ管理の実装前に設計します。

### 4.3 ZIPの受け渡し情報

| 項目 | 扱い |
|---|---|
| ギガファイル便のダウンロードURL | 必須。HTTPSのギガファイル便URLを案内し、フォームで制限できる範囲を確認する。管理者もホスト名を確認する |
| 保持期間 | 必須、7日以上。初期値は `7`。`7日` / `7日間` も入力可とし、送信時は数値文字列に整形する。管理者も取得前に確認する |
| ダウンロードキー | 設定した場合に入力する |

プロジェクト側でURLへの自動アクセス・ダウンロード・展開は実装しません。管理者が確認して取得します。

## 5. 作者の操作フロー

### 手順1：作品と素材を確認する

- ［検査］と［試遊］で確認する。
- 素材管理に必要な画像・音声を登録する。
- 素材の不足、未使用素材、作者名、ライセンスを確認する。

検査結果は、提出を止めるエラーと、確認を促す警告に分けます。共通素材まで「未登録の素材」と誤判定しないようにします。

シナリオ固有素材は、従来の外部配信先で表示・再生できても、ローカルに未登録なら不足として対象パスを通知します。試遊できることを、提出ZIPに素材がそろっている根拠にはしません。外部配信先から自動取得して不足を隠すことも行いません。

### 手順2：提出画面を開く

既存の［投稿…］を新しい［提出…］に置き換えました。Playground内にZIP作成、ギガファイル便へのリンク、投稿情報の入力画面を実装し、オレンジフォームへPOSTします。実際の受付・メール送信には、オレンジフォームの管理画面での設定が必要です。

### 手順3：ZIPを保存する

- 収録内容と合計サイズを表示する。
- シナリオIDを確認し、保留中のシナリオ編集・素材操作の保存を完了する。保存に失敗した場合は通知してZIP生成を中止し、古い保存内容で代替しない。
- 保存完了後、シナリオJSONと登録素材の同一時点のスナップショットを取得する。取得中の変更が混ざらないようにし、その後の編集は生成するZIPに反映しない。
- シナリオ本体と登録素材を `<id>.zip` としてダウンロードする。
- 作品を変更した場合は、改めてZIPを作成してアップロードする必要があることを案内する。
- ブラウザーから実際の保存完了を確認できない場合は、「保存完了」と断定せず、ダウンロード先の確認を促す。

ZIP作成に使ったスナップショットの作品情報・分類・紹介文を投稿フォームの初期値に使い、後から編集された作品の情報と、すでにアップロードしたZIPの情報を混在させないようにします。スナップショット取得後のZIP生成処理自体は、保存データを削除・変更しません。

### 手順4：ギガファイル便にアップロードする

- ［ギガファイル便を開く］で新しいタブを開く。
- 利用者がZIPをアップロードする。
- 管理者が取得できる十分な保持期間を選ぶよう案内する。
- ダウンロードキーの設定を勧める。
- アップロード完了後、ダウンロードURL・保持期限・キーを控えてPlaygroundに戻る。

ギガファイル便への自動アップロードや、同サイトの画面操作の自動化は行いません。

### 手順5：投稿情報とURLを入力する

既存画面の次の項目を維持します。

- 連絡先（メールアドレス）
- 分類
- 難易度
- シナリオ紹介
- 作者より

Playground内のフォームで、上記項目と作者名、ダウンロードURL・保持期間・ダウンロードキーを確認・入力します。作者名・分類・紹介文はシナリオから初期値を設定します。作品名・シナリオIDはZIP内の `scenario.json` のみを正式な情報源とし、画面表示に限って受付フォームには送信しません。

Playgroundは利用者の明示的な操作でオレンジフォームへ `application/x-www-form-urlencoded` のPOSTを行います。シナリオJSON、画像、音声、ZIPのファイル本体は送信しません。

### 手順6：確認して送信する

Playground内で入力を確認し、［作品を提出］ボタンで別タブへPOSTします。別タブで内容を確認して最終送信します。入力の不備はPlaygroundに、通信・受付のエラーは別タブに表示されます。元の入力は保持します。別タブが開かない場合はブラウザーの設定を確認してください。

フォームから送るのはテキスト情報だけです。シナリオJSON、画像、音声、ZIPのファイル本体は送信しません。ファイル添付欄は設けません。

### 手順7：受付結果を確認する

- 別タブの受付結果と、連絡先に届く確認メールを確認する。届かない場合は迷惑メールフォルダーも確認する。Playground側では受付・メール配送の完了を判定できない。
- 受付と公開は別であり、管理者の内容確認後に公開する。
- Playgroundの入力はキーを除いてCookieに30日間保持する。通信失敗・再試行が可能で、成功応答を読み取れない状態で入力を自動消去しない。
- 成否が不明な場合の問い合わせ方法を示す。連打・再投稿による重複の可能性は管理者側でも確認する。
- 投稿機能が正しく動作しない場合は、ダイアログ下部の補足リンクから既存のGitHub Discussions経由で提出できるようにする。公開の投稿欄へ連絡先やダウンロード情報を書かないよう注意を添える。

代替の提出先：<https://github.com/snext1220/stext/discussions/299>

## 6. ZIPの構成

既存の案内に合わせ、シナリオごとのフォルダー構成にします。

```text
forest01/
  scenario.json
  capture/
    intro.png
    hut.png
  bgm/
    main.mp3
    se/
      door.mp3
```

- 出力対象のシナリオの登録済み固有素材は、未使用のものも含めて収録する。別作品の素材は収録しない。提出前に一覧から確認・削除できるようにする。
- 使用していないフォルダーは作らない。
- シナリオ固有のキャラクター画像を扱う場合は、既存の素材参照仕様に合わせて配置する。
- 共通素材とプレイヤー本体は収録せず、共通素材の参照は維持する。したがって、ZIP単体で動くアプリではない。
- ZIP内のパスやシナリオIDを検査し、フォルダーの外を指す名前や重複した参照先を許さない。
- ローカル保存用ZIPに、連絡先・ダウンロードキーなどの提出情報を不用意に含めない。

## 7. オレンジフォームの設定と運用要件

### 7.1 フォームの設定

- [development.md](./development.md) に従い、フォームID `261098` の管理者通知と `mail` 宛ての自動返信（確認メール）を設定する。
- 発行HTMLと項目名・hidden値・honeypotが一致することを確認する。フォームを再発行・変更した場合はコードとテストを更新する。
- 必須項目、文字数、入力検査、迷惑投稿対策、完了画面を設定・確認する。クライアントの検査はサーバー側検査の代替ではない。
- 確認画面・最終送信・受付記録・通知・自動返信の一連の動作を本番Playgroundから確認する。
- ZIP本体は受け取らない。ギガファイル便への自動アクセスやダウンロードも行わず、管理者がURLと保持期限を確認する。

### 7.2 メールと個人情報

- 投稿情報、連絡先、ダウンロードURL、任意のキーを管理者通知に含める。フォームの受付データと受信箱の閲覧権限、保管期間、削除方法を定める。
- 管理者が許可したテスト投稿で、管理者通知と確認メールの到達・迷惑メール判定・文字化けを確認する。自動テストでは実送信しない。
- 自動返信の本文と送信元を確認する。URL・キーを含めるかは必要性を検討し、誤入力やなりすましへの対応も確認する。
- 受付と同時の自動公開は行わない。管理者が内容とZIPを確認してから公開する。

### 7.3 旧受け口

- 旧 `upload.php` へのクライアント送信コードは削除済み。旧サーバー側受け口は公開環境で別途停止する。
- 独自 `submit.php` はリポジトリから削除済み。公開環境に配備済みの場合は停止し、旧URLへの転送や受付継続がないことを確認する。`VITE_SUBMISSION_URL` は廃止。

## 8. 管理者の操作フロー

1. 管理者宛てメールで投稿情報・URL・保持期限を確認する。ダウンロード前にURLのホスト名を確認する。
2. 期限までにZIPを取得する。
3. 展開前に、パス・ファイル種別・サイズ・構成を確認する。ZIP内のファイルを不用意に実行しない。
4. シナリオの検査、素材の確認、試遊を行う。
5. 必要に応じて作者に修正を依頼する。
6. 確認後、`scenarios/<id>/` に配置し、公開する。

任意の追加機能として、ZIPの構成・パス・サイズ・シナリオを確認するCLIを検討します。コマンド名や実装範囲は未決定です。

## 10. 確認項目

- ZIPにシナリオと登録素材が入り、フォルダー構成と参照が一致すること。
- 共通素材や提出者の連絡先・キーが、ZIPに混入しないこと。
- 素材の不足・未使用、保存失敗、ZIP生成失敗を適切に表示すること。
- 固有素材は外部配信先で表示・再生できても未登録なら不足を通知し、共通素材の未登録は不足扱いにしないこと。
- 編集直後のZIPにも最新の内容が入り、保存失敗時は生成を中止すること。生成中の変更が混ざらず、投稿フォームの初期値も同じスナップショットに基づくこと。
- ID未設定でもローカル編集・素材登録ができ、IDの設定・変更で素材との対応が失われず、同じIDの別作品と素材が混ざらないこと。ZIP生成前にはIDの修正を求めること。
- 必須項目、文字数、難易度、URL、保持期間、キーの検証を行い、フォーム側の必須設定と整合させること。
- 発行HTMLの項目名・hidden値・honeypotを送り、著作権表示を残すこと。
- 不正入力では遷移しないこと。正しい入力ではUTF-8のPOSTで別タブへ送り、元の画面と入力を保持すること。外部script・`fetch` は使わないこと。
- 別タブの受付・メール送信結果をPlayground側で成功と表示しないこと。
- キー以外の全入力がプロジェクトごとにCookieへ30日間保存され、復元・個別削除できること。保存失敗を警告すること。ダウンロードキーはCookieに含めず、連絡先やダウンロード情報をZIPに含めないこと。
- ZIP本体をオレンジフォームへ送らず、旧サーバー側受け口が停止していること。
- 本番で確認画面と最終送信、受付記録、管理者通知と確認メールの到達、文字化け、迷惑メール判定、送信元設定を確認すること。
- 別タブとの行き来、スマートフォン、キーボード操作でも手順を進められること。
- 既存のJSON保存・読み込み・試遊などの動作を維持すること。
